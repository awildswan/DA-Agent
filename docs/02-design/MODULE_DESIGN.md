# 模块详细设计（MODULE_DESIGN）

> 编号：02-design/MODULE_DESIGN · 版本 v0.1 · 2026-11-22 · 状态：Draft
> 15 环节逐一设计。模板（每环节 8 段）：**目标 / 输入→输出 / 状态与工具 / 守卫·校验 / prompt 结构 / 设计取舍 / 借鉴出处 / 测试点**。

## ① 召回知识

- **目标**：每个问题回合（含同会话追问）取数前，先对照知识库大纲召回相关口径 / 语义 / 守卫声明 / 排障经验，杜绝每会话从零开始。
- **输入 → 输出**：输入 = 用户本轮问题 + 会话历史（含本会话刚写入的知识）；输出 = 召回的知识块（concepts / tables / selections / playbooks / users / 守卫声明）。
- **状态与工具**：工具 `search_okf_knowledge` / `load_okf_knowledge`（name 只能来自大纲 / list / search）；状态 = OKF 知识库（git 版本化）+ 知识大纲（catalog 渲染）。
- **守卫 / 校验**：知识条目名纪律——load 的 name 禁止编造；「开局必召回」是可机械检查的打分维度（首个工具是否为 search_okf_knowledge）。
- **prompt 结构**：静态 preamble 只放「每问取数前先对照大纲召回（含本会话刚写入的）」这条纪律；动态 = OKF 大纲快照放 `<runtime_context>`，不进 system prompt。
- **设计取舍**：为什么「必召回」而非「按需检索」？——召回不全会直接造成交付缺披露（daw 案例：漏召回 gmv_reconciliation → 没披露放款张力）；确定性纪律比模型自觉可测。
- **借鉴出处**：daw 原则⑤（沉淀→召回→按沉淀交付）+ AGENTS.md R15（开局召回纪律）。
- **测试点**：跨会话验收（会话 A 沉淀 → 新会话 B 召回并直接按沉淀交付）；eval 断言首个工具是 search。

## ② 语义映射

- **目标**：把业务语言（"定金""有效单"）映射到表 / 字段 / 筛选条件；**先给业务理解 + 口径，让用户确认 / 纠正**，确认后立即沉淀。
- **输入 → 输出**：输入 = 召回的知识 + 用户问题；输出 = 业务理解陈述 + 采用口径 →（用户确认后）映射写入 OKF concepts / tables。
- **状态与工具**：OKF concepts / tables（业务知识）；工具 = load / write_okf_knowledge；用户确认是一次对话交互。
- **守卫 / 校验**：「确认后的映射必须立即沉淀」——write 落盘检查（fail-loud，工具报成功 ≠ 已落盘）。
- **prompt 结构**：静态 = 「业务概念：语义映射是你的职责」小节（先给业务理解再给数字；符合业务理解的数字，不是数据库准确的数字）；动态 = 本问涉及的概念与候选口径。
- **设计取舍**：为什么「先给理解再给数字」而非默默选口径？——说出理解后被纠正一次，远好过默默选一个让用户猜。
- **借鉴出处**：daw 原则② + AGENTS.md R8（用户元反馈「我要的是符合业务理解的数字」）。
- **测试点**：eval case：新概念问题，agent 先说理解再取数；确认后新会话 B 直接沿用不再问。

## ③ 规划 / 拆解

- **目标**：把复杂问题拆成子查询 / 多步（对比、同比环比、多表对账、趋势 + 归因）；单跳问题跳过。「像你我一样」的关键体现。
- **输入 → 输出**：输入 = 已确认语义的问题；输出 = 执行计划（子任务列表，每个子任务 = 一次取数，各自独立可验证）。
- **状态与工具**：计划状态（plan + 子任务状态机）；V1 用结构化 plan，不引入多 Agent。
- **守卫 / 校验**：「多数字自洽自检」——同域大数必须交代关系、差额负责到零；子任务之间是否闭合。
- **prompt 结构**：静态 = 计划纪律（先规划再取数；多步问题拆解；每个子问独立可验证）；动态 = 问题本身 + 已知口径。
- **设计取舍**：V1 用「显式计划状态机」而非 LangGraph / 多 Agent——单 Agent 的规划够用，多 Agent 编排留 V2 再评估 LangGraph。
- **借鉴出处**：书目第 1 章（ReAct / 规划）+ daw playbooks（把偶发高质量交付固化成协议）+ comet 多 Agent 编排（V2）。
- **测试点**：eval case：对比两指标问题拆成两个子查询并分别对账；同比环比问题拆窗。

## ④ 穷尽探查

- **目标**：在说「数据里没有」之前穷尽手段找表 / 字段：命名族扫描、概念同义词多轮轮扫、重点找 `is_*` / `type_*` / `status_*` 官方标记、值域分布验证；**权限被拒 ≠ 概念不存在**。
- **输入 → 输出**：输入 = 需要的业务概念；输出 = 定位到的表 / 字段 / 视图 + 注册信息（table_registry）。
- **状态与工具**：`table_registry`（技术元数据：access_mode / table_type / status / connection）+ OKF tables（业务知识）；工具 = `list_tables` / `list_remote_tables` / `register_table` / `describe_table` / `sample_data`。
- **守卫 / 校验**：裸引远端 catalog 预执行守卫（`FROM "yantubi"."t"` 拦截并给对症修法）；pushdown 表禁走短名视图；权限 / 不存在 / 存储层级错误对同表是**终局**（不重试、不绕行）。
- **prompt 结构**：静态 = 探查纪律（穷尽探查才说「没有」；找官方标记字段；权限 ≠ 不存在）；动态 = 候选表清单 + 表元数据。
- **设计取舍**：技术元数据（table_registry）与业务知识（OKF）**分层**，访问模式抽象成 catalog vs pushdown——不整库倒表，按问题只取相关表 / 字段。
- **借鉴出处**：daw 原则② + `table-metadata-spec.md` + AGENTS.md R18（裸引远端守卫）。
- **测试点**：eval case：新数据源首连时穷尽探查而非直接说「没有订单表」；foreign table 走 pushdown 不被误伤。

## ⑤ 生成 SQL

- **目标**：把已确认语义、已探查 schema 的取数意图，生成正确方言的 SQL（多方言 / 下推抽象）。
- **输入 → 输出**：输入 = 语义确认 + 表 / 字段定位 + 计划子任务；输出 = SQL 文本（带方言、下推方式）。
- **状态与工具**：模型生成；方言抽象（普通表走 catalog 视图，foreign 表走 `postgres_query` 下推）；`sqlglot` 做解析 / 方言转换 / 结构静态校验。
- **守卫 / 校验**：生成阶段用 `sqlglot` 做静态预检（语法、危险关键词、方言合法性）；重守卫（禁词词边界 / 裸引远端）放到⑥执行前。
- **prompt 结构**：静态 preamble 放生成纪律（SQL 风格、口径、下推规则 **owner**）；动态 runtime_context 放 schema 裁剪结果 + 表元数据 + 口径。**字节稳定**：每次生成同一静态 preamble，schema 结果走 runtime_context。
- **设计取舍**：为什么用 sqlglot 机械校验而非纯靠模型？——「机械对账 > 模型自觉」；方言转换交给 sqlglot 而非手写。
- **借鉴出处**：daw 静态 / 动态 prompt 分离 + 「每个事实只有一个 owner」（下推规则 owner 是 preamble）。
- **测试点**：生成 SQL 通过 sqlglot 解析；方言转换正确；危险操作被静态预检拦截。

## ⑥ 执行

- **目标**：在只读守卫下执行 SQL，返回结构化结果 + 元数据（行数 / 耗时 / firstRow 指纹）。
- **输入 → 输出**：输入 = 通过静态校验的 SQL；输出 = 结构化 SqlResult（columns / rows / meta）+ 错误分类。
- **状态与工具**：工具 `execute_query` / `run_query` / `render_chart`；执行层 = DuckDB + 数据源连接（catalog 别名）。
- **守卫 / 校验**（执行侧，**宁误拦不漏放**）：
  - 只读禁词守卫：`DROP/DELETE/UPDATE/ALTER/TRUNCATE/INSERT` 等，**词边界匹配而非子串**（`is_deleted` 不误伤），先抹字符串字面量再匹配，引号未闭合退回保守子串；
  - 裸引远端 catalog 预执行守卫：`FROM "yantubi"."t"` 拦截 + 对症修法（短名视图 / 整段包 postgres_query）；
  - 超时、行数上限（`queryRowLimit` 动态注入）、并发控制；
  - 错误分类器：按真实错误原文分类（table_missing / column_missing / function_missing / operator_mismatch / permission / resource_limit / type_not_supported / storage_tier / timeout / syntax）+ 对症建议；权限类 = **终局不重试**。
- **prompt 结构**：工具描述动态注入当前 `queryRowLimit`（preamble 不写死数字，字节稳定）；错误处置决策树 owner 在 preamble。
- **设计取舍**：禁词为什么用词边界不用子串？——`contains("DELETE")` 会误伤 `is_deleted` 列名，把模型逼向更差 SQL；分类器测试用例为什么取自真实原文？——「守卫解析器必须吃 LLM 真实输出形状」。
- **借鉴出处**：daw 禁词守卫 + 错误分类器 + postgres_query 关键经验（第一参数必须是 catalog 别名）+ R18（裸引远端守卫）。
- **测试点**：禁词守卫用例用真实翻车 SQL（多行 / CTE / 中文过滤值）；`is_deleted` 不误伤；foreign table pushdown 正常执行。

## ⑦ 交付闸门（灵魂）

- **目标**：交付前对结论做**机械对账**，拦下「结构对但数字 / 口径错」的答案；红灯触发⑧自纠。
- **输入 → 输出**：输入 = 执行结果 + 结论文本；输出 = 通过 / 红灯（含红灯清单与原因）。
- **状态与工具**：`delivery_check` 组件；知识库里的守卫声明（`允许 / 禁止 / 关系 / 核对`）。
- **守卫 / 校验**（三种守卫，**宁漏不误**——低误报才有公信力）：
  1. **值域守卫**：结论实体（部门 / 区 / 组等组织后缀）∉ 声明允许值域 → 红灯；实体抽取剥前缀散文 + 零使用语境降级（近旁有「没用 / 未收 / 零」→ warn 不判红）；
  2. **关系守卫**：声明 `关系: 放款总额 ≈ 分期GMV 容差2% 解释词:同秒、重复 必须披露`；两侧金额提取（万 / 亿归一，计数单位跳过，无单位数字不接受）→ 差额超容差且无解释词 → 红灯；「必须披露」= 一侧缺席 → warn；
  3. **核对 SQL 直查真值**：声明 `核对:SELECT ...`（返回一行两列 = 左右真值）；红灯触发自纠前直查该 SQL，真值逐侧与结论数字比对（容差 1%），接地行两路投放（用户可见 + 进修正指令）——**自纠幻觉变机械不可能**。
- **prompt 结构**：守卫声明是知识库新物种（**被机制执行，不只被引用**）；修正指令模板化（「每个数字必须来自本会话实际执行的查询，查不到就写不存在」）。
- **设计取舍**：为什么闸门「宁漏不误」而执行守卫「宁误拦不漏放」？——执行侧是安全底线，误放 = 删库；闸门侧误报会打断交付、透支信任，所以低误报优先。
- **借鉴出处**：daw `delivery_check.rs`（值域 R13/R16 + 关系 R16 + 核对 SQL R17）+「模板化纪律 > 说教纪律」。
- **测试点**：值域守卫抓层级错配（部门 ≠ 战区）；关系守卫抓「只报 GMV 不披露放款」；核对 SQL 抓自纠幻觉；夹具全用真实翻车原文。

## ⑧ 自纠环

- **目标**：红灯后 in-context 续跑自纠（带接地纪律）→ 复检，≤2 轮；仍有残留 → 如实披露。
- **输入 → 输出**：输入 = 红灯清单 + 接地真值；输出 = 修正后的结论（再过闸门）。
- **状态与工具**：runner 支持 loop 续跑（in-context，非新会话）；修正指令 = 红灯清单 + 接地真值 + 接地纪律。
- **守卫 / 校验**：复检（每轮产出都再过闸门）；最多 2 轮；环耗尽仍有红灯 → `delivery_check` 事件 + 文本通道如实披露「自纠 N 轮后仍有 M 项未消除，请人工复核」，绝不装干净交付。
- **prompt 结构**：修正指令模板化——红灯专用纪律（差额构成落到具体数字，禁一句「口径不同」带过）+ 接地纪律（每个数字来自本会话实际查询）。
- **设计取舍**：为什么 in-context 续跑而非新会话重建？——新会话会丢上下文（daw 曾用全新会话当第二段，效果差）；为什么 ≤2 轮 + 如实披露？——机制拦不完的必须明说（fail-loud）。
- **借鉴出处**：daw 自纠环（R16/R17，in-context + 接地 + 复检）+「接地纪律让幻觉机械不可能」。
- **测试点**：自纠段数字与真值一致；幻觉数字被核对 SQL 拦截；2 轮后残留被如实披露。

## ⑨ 交付

- **目标**：按交付纪律给出取数答案（先答所问 + 出处 + 业务结构；残留如实披露）；业务诊断留到 ⑩。
- **输入 → 输出**：输入 = 通过闸门的结论 + 执行结果；输出 = 结构化交付（数字 / 口径 / 来源 / 业务结构 / 图表 / 估算标注）。
- **状态与工具**：交付模板（「来源：」行等）；图表渲染 `render_chart`；用户画像（沟通与交付偏好）。
- **守卫 / 校验**：交付模板化（可机械检查：来源行、口径词、首句数字、禁词）；「来源：」行缺失 = 未完成交付；残留披露检查。
- **prompt 结构**：静态 = 交付纪律（先答所问 / 带出处 / 默认有效口径 / 带业务结构 / 允许估算标注成分）；**模板化纪律**（来源行格式）比说教更可遵守；原则⑥轻量改造——标注推断依据 + 指出数字在业务里的位置。
- **设计取舍**：为什么把纪律写成模板而非说教？——daw R9 剂量-响应：说教（0%）→ 要求有行（v2）→ 规定行格式（v3），合规率单调上升。
- **借鉴出处**：daw 原则③ + R7/R8/R9（交付纪律 + 模板化）+ 原则⑥轻量改造。
- **测试点**：eval 断言「来源：」行存在、首句先答数字、禁词零出现；估算标注成分。

## ⑩ 业务诊断与决策辅助

- **目标**：在「先答所问」基础上，**按需**给出业务解读与行动建议——结果意味着什么 → 是否值得采取措施 → 结合业务背景提出建议并评估影响；问「为什么 / 怎么办 / 值不值得」时才进入，问「是多少」时不擅自升级。
- **输入 → 输出**：输入 = ⑨ 交付的数字 + 口径 + 业务结构 + 全局业务模型（OKF）；输出 = 诊断结论（变化发生在业务链路哪一层、意味着什么）+ 建议（是否值得采取措施）+ 影响评估（量级 / 方向 / 置信度）。
- **状态与工具**：OKF 业务概念（商业模型 / 价值链锚点 / 业务机制）+ 用户画像（观点 / 关注点）；无新增工具，复用已召回的知识。
- **守卫 / 校验**：推断必须**标注依据**（数据锚点 / 业务机制 / 推断待验证），区分「实测」与「推测」；诊断不推翻 ⑨ 的先答所问纪律；建议必须可回退到数字。
- **prompt 结构**：静态 = 「业务诊断：结论 → 依据 → 建议 → 影响」结构纪律 + 推断标注依据；动态 = 本问数字、口径、业务结构与全局模型。
- **设计取舍**：为什么从「轻量改造」升级为显式环节？——用户要的不只是数字，是「这个数字对我意味着什么、要不要动手」；但**必须先答所问再诊断**（原则③ 不破），诊断是第二层不是替代。
- **借鉴出处**：daw 原则⑥（数字是手段，看懂生意并指向利润改进才是目的）+ R12（「毫无智能」元反馈：一问一答、答完即忘不是智能）。
- **测试点**：eval case：问「销量下滑了怎么办」→ 先给下滑数字 + 口径，再给归因（标注依据）+ 建议 + 影响；问「销量多少」→ 不擅自升级成诊断。

## ⑪ 沉淀

- **目标**：把本会话学到的（字段释义 / 口径 / 排障经验 / 用户偏好 / 任务协议）立即沉淀进 OKF 知识库；**修正优先于并存**；git 版本化可回溯。
- **输入 → 输出**：输入 = 本会话的映射确认 / 纠错 / 排障 / 新发现；输出 = OKF 知识变更（git commit + ±行数回执）。
- **状态与工具**：OKF 知识库（git 版本化）+ 用户画像（users）+ 任务协议（playbooks）；工具 = `write_okf_knowledge` / `update_okf_metadata` / `search` / `load`。
- **守卫 / 校验**（daw 用血泪换来的，全保留）：
  - 写入守卫：空 content 拒写（fail-loud 指路）；content 以 frontmatter 开头（整文件特征）拒绝；`heading=all` 拒绝；标题归一化匹配（norm_heading）防近似重复；剥离回显同名标题（防吞正文）；
  - 修正优先于并存：改口径后 **grep 全库清零旧定性词**，只改权威条目 = 没改完；`status=active/superseded` 生命周期；
  - git 版本化 + 回执：每次写入自动 commit（提交信息带板块名 + ±行数）；净删 ≥5 行且零新增 → 当场警告；
  - fail-loud：「工具报成功」≠「知识落了盘」，对账以磁盘文件 / git 审计为准。
- **prompt 结构**：静态 = 沉淀纪律（学到立即沉淀、修正优先于并存、追加必须带全量旧条目）；动态 = 本会话确认的映射 / 纠错。
- **设计取舍**：知识为什么 git 版本化而非数据库？——可回溯、可对账、diff 是审计铁证；为什么「修正优先于并存」？——新旧并存逼下次会话当仲裁，既耗推理又易选错。
- **借鉴出处**：daw 原则④ + `okf/store.rs` 写入守卫 + R10（吞正文）/ R13（修正优先于并存）/ R14（T+1 残留）。
- **测试点**：空 content 拒写；frontmatter 误存拒写；近义标题归一化合并；git 回执 ±行数正确；grep 清零验证。

## ⑫ 复盘（离线）

- **目标**：用真实使用 transcript 复盘，找问题 → 配测试修复 → 再用验证（**用-查-改-用**循环）；复盘工具是产品的一部分。
- **输入 → 输出**：输入 = 真实会话 jsonl（`payload` 字段存结构化 SqlResult）；输出 = 复盘报告（工具时间线 / 慢查询 / 错误归因 / 一致性体检 / 知识库体检 / git 审计 / 纠正候选）。
- **状态与工具**：`review_transcript.py`（复盘）+ `verify_claims.py`（值域对账）+ `okf_cleanup_stubs.py`（残桩清理）；对账以 payload 为准（logs 表只有摘要，别指望它回放结果）。
- **守卫 / 校验**：对账手法——payload 三处一致（summary 声明 / meta.rows / rows）；git 审计（最近 N 次知识变更 + 未提交变更检测）；知识库体检（空板块 / 真损失 / 残桩分类）。
- **prompt 结构**：无（离线脚本）；但复盘产出分两层——「产品方法论」进 DESIGN_PRINCIPLES（去业务化），「业务口径」进用户本地知识库（不进仓库）。
- **设计取舍**：为什么复盘是产品的一部分而非侧脚本？——「越用越懂」没有复盘就是口号；复盘工具自身也有盲区（工作区 okf 在 ~/.daw 之外 → `okf_roots()` 枚举全部工作区）。
- **借鉴出处**：daw 用-查-改-用循环 + `review_transcript.py` + R 系列复盘。
- **测试点**：复盘脚本自测；git 审计抓未提交变更；知识库体检抓空标题残桩。

## ⑬ 打分（离线）

- **目标**：对任意真实会话**无金牌**打分（五维），把复盘从定性升级为定量，最弱维度 = 下一个改进工单。
- **输入 → 输出**：输入 = 会话 jsonl；输出 = 五维分数 + 最弱维度定位。
- **状态与工具**：`session_score.py`；配置覆盖（ban_words / weights / disabled_checks，词表增长不改代码）；SCORING_VERSION 管版本。
- **守卫 / 校验**：`--selftest`（合成好 / 坏会话，分数方向断言）+ `--calibrate`（已知历史会话分数方向与人工判断一致）。
- **prompt 结构**：无（离线打分）。五维：D1 交付形态 0.30 / D2 效率稳定 0.15 / D3 知识行为 0.20 / D4 验证倾向 0.10 / D5 用户验收 0.25。
- **设计取舍**：为什么判别力校准是上线门槛而非可选项？——「结构正确 ≠ 真相」在打分层重演（首版结构分 91.8 A，加 D5 用户验收后降到 80.8 B，最弱维度准确指向问题）。
- **借鉴出处**：daw `session_score.py` + R13（用户验收维度）+「不断完善本身是机制」。
- **测试点**：`--selftest` 通过；`--calibrate` 方向一致；最弱维度准确指向真实问题。

## ⑭ 生产四要素（贯穿全程）

> ⑭ 是横切关注点而非线性环节，采用略简格式：**目标 / 关键设计 / 借鉴出处 / 验收**。

### Eval 评测

- **目标**：让「改 prompt / 换模型是否退化」可度量。
- **关键设计**：**两层评测**（见 TEST_PLAN.md）——L1 自制业务口径集（数字命中 / 来源标注 / 首句先答 / 口径正确 / 交付闸门红灯，对齐 daw）；L2 Spider / BIRD 子集（SQL 执行准确率回归，附诚实污染声明）；金牌复标 SQL **钉在直查新鲜值上**（防 ETL 漂移）；无头跑器 + 打分器（评分对象 = 最后一次工具调用后的结论文本）；**评测只读闸门**（`eval-` 任务写工具全拒）；换模型 n=3 对照区分「稳定行为 vs 抽样噪声」。
- **借鉴出处**：comet 三层评测（自制 + 公共基准）+ pi 隔离 AB + daw 评测四件套（业务口径集）。
- **验收**：每次改 prompt / 模型跑回归；评测 run 前后 OKF 仓库 HEAD 一致（零提交）。

### Trace 可观测

- **目标**：出错能逐帧回放，定位是哪一环崩的。
- **关键设计**：①~⑨ 每环节打 span（问题 → 澄清 → 召回 → 探查 → SQL → 校验 → 执行耗时 / 行数 / firstRow 指纹 → 答案）；OTel 风格 trace / span 双表 + ContextVar 自动 parent + 异步批量落库不阻塞主流程 + 按模型单价核算成本；**firstRow 指纹**作为引擎级不确定性对账手段。
- **借鉴出处**：comet OTel tracing + daw firstRow 指纹（P0-B 时区 bug 的定位手段）。
- **验收**：一次错误可回放定位到具体环节；成本可按 model 核算。

### Deploy 部署

- **目标**：可打包、可生产收紧、可降级。
- **关键设计**：桌面打包（Tauri v2，见 ARCHITECTURE.md）+ 只读账号连真实库；超时 + 强制 LIMIT + 并发控制；模型失败降级转人工 / 给出最接近 SQL 让用户确认；pydantic-settings 统一读 .env，LLM Key 加密入库不进 .env。
- **借鉴出处**：comet 配置管理 + daw 本地优先。
- **验收**：打包产物可分发；只读账号无法写库；模型故障时优雅降级。

### Security 安全

- **目标**：不删库、不越权、不泄敏、不 prompt 注入。
- **关键设计**：只读权限兜底 + 危险操作词边界拦截（DROP / DELETE / UPDATE / ALTER / TRUNCATE）+ 行级权限（运营只看自己区域）+ 敏感列脱敏（手机 / 身份证）+ 防 prompt injection（作为已知风险写明）；**SECURITY.md 显式信任边界 + out-of-scope**（借 pi 写法）。
- **借鉴出处**：pi `SECURITY.md` + daw 只读禁词守卫 + comet 工具白名单。
- **验收**：危险 SQL 全被拦截；越权查询被行级权限挡住；敏感列输出脱敏。

## ⑮ 会话状态与上下文管理（贯穿全程）

> ⑮ 是横切关注点而非线性环节，采用略简格式：**目标 / 关键设计 / 借鉴出处 / 验收**。

### 会话状态（短期记忆）

- **目标**：同一会话内，追问（"那华南呢？"）能引用前文（"华东的销量"），不必重复语境。
- **关键设计**：会话内维护消息历史 + 结构化状态（已确认口径、已探查的表、本会话中间结果）；每轮把相关历史注入 prompt。与长期记忆（OKF）**分层**：会话内临时、跨会话才沉淀 OKF。
- **借鉴出处**：书目第 3 章（会话记忆）+ daw「每个问题回合（含同会话追问）先对照大纲召回」。
- **验收**：追问"那华南呢"能正确续上前文的区域与口径。

### 上下文管理（压缩 / 窗口）

- **目标**：长会话不撑爆上下文窗口、不击穿前缀缓存、成本不随历史线性增长。
- **关键设计**：静态 / 动态 prompt 分离（字节稳定，已有）；超长历史做**压缩**（旧轮次总结成大纲，不逐字保留）+ **窗口裁剪**（只留最近 N 轮 + 关键状态）。压缩阈值与摘要方式需真实数据调参。
- **借鉴出处**：书目第 2 章（上下文压缩 / KV Cache）+ daw 静态 / 动态分离（字节稳定 system prompt）。
- **验收**：长会话 token 不随历史线性增长；压缩后追问仍能正确引用关键口径。

### 多轮状态机

- **目标**：把「澄清 / 确认 / 纠正」这些需用户回应的点，做成显式多轮状态（反问 → 等确认 → 继续）。
- **关键设计**：runner 支持 pause / 继续——澄清问题回给用户，用户回答后 resume 同一会话；**确认后才沉淀**（配合 ② 语义映射）。
- **借鉴出处**：daw「先给业务理解 + 口径，让用户确认 / 纠正」+ AgentHerd fail-toward-human（不确定就上报）。
- **验收**：遇歧义口径时反问，用户确认后继续并沉淀。
